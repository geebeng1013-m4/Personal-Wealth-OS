1.产品概述

1.1 产品是什么

WealthUp（内部代号 Personal Wealth OS）是一个面向个人的理财操作系统，把「现金流分配 → 强制定投 → 记账 → 漏财检测 → 月度复盘」串成一个闭环，而不是一个只用来"看余额"的记账本。产品的核心假设是：多数人理财失败不是因为不会算账，而是因为缺乏一套会强制执行的规则和一个诚实的月度反馈循环。

1.2 要解决的问题

  • 现金流没有分配机制：发薪之后钱没有被提前"分格"，容易被日常消费吃掉，导致定投计划形同虚设。
  • 投资纪律依赖意志力：普通记账 App 不会提醒用户"这个月的 DCA 做了没有"，也不会在市场下跌时给出可执行的加码规则。
  • 小额漏财难以被发现：订阅费、银行手续费、重复扣款等小额支出零散地藏在流水里，人工很难发现。
  • 投资持仓与记账是两套系统：交易记录（moomoo 等券商导出的 CSV）和日常记账通常互不相通，用户很难看到"整体净资产"。

1.3 产品定位与边界（Non-goals）

以下是当前版本明确不做的事情，避免范围蔓延：

  • 不是持牌财务顾问或投资建议服务——"顾问"模块给出的是基于规则的机械化提示，不构成投资建议。
  • 不是多租户 SaaS——当前架构假设每个 Firebase 项目服务一个人或一个家庭，没有团队协作、多用户共享账本等概念。
  • 不对接真实券商 API 做自动同步——交易数据通过手动录入或 CSV 导入（目前针对 moomoo 的导出格式做了专门解析）。
  • 不做多币种记账系统——记账本身以 MYR 为准，投资侧的美元/马币汇率折算是唯一的多币种场景。

2.目标用户与使用场景

2.1 目标用户画像

主用户画像：年轻定投者

在校生或刚出社会的年轻专业人士，收入以固定津贴/月薪 + 不定期收入为主，正在用 moomoo 之类的券商定投美股 ETF（VOO / QQQM / VXUS 等），以 MYR 记账、以 USD 交易，风险偏好偏高、投资期限长（20–30 年）。这类用户的痛点不是"没钱投资"，而是"没有把纪律坚持下去的系统"。

2.2 核心使用场景

场景一：发薪日的资金分配

用户在 Budget（Buckets）页面把到手津贴按既定比例分配到安全垫、成长（定投）、自由、学习、机会等资金桶，明确每个桶月度/一次性金额，避免钱在到账当天就被日常消费吸收。

场景二：月度定投与交易导入

用户按 DCA Plan 中配置的 VOO/QQQM/VXUS 目标比例在 moomoo 下单，随后在 Portfolio 页面通过 CSV 导入交易记录（系统自动识别 moomoo 万能账户导出格式，或退回到通用 CSV 列名匹配），系统据此计算持仓、加权平均成本、已实现/未实现盈亏，并标注配置漂移（drift）是否超过 8% 阈值。

场景三：市场下跌时的机会储备部署

当大盘出现回撤，用户在 Advisor / Rules 中查看预设的三档"熊市加码"梯度（-10% / -15% / -20% 回撤各对应一定比例的机会储备），按规则而非情绪决定是否加码，避免"越跌越怕、越涨越贪"的行为偏差。

场景四：日常记账与漏财发现

用户在 Ledger 记录日常收支与转账，系统在后台跑 8 类"漏财"检测（订阅费、手续费、重复扣款、支出异常上涨、异常单笔支出、预算超支、目标停滞、债务拖累），在 Money Leaks 页面汇总为可操作的清单，而不需要用户自己逐笔翻账单。

场景五：月度复盘

月末，用户在 Review 查看系统给出的「自律分数」（储蓄率 + DCA 达成率 + 记账完整度加权），判断这个月的执行力，为下个月调整分配比例提供依据。

3.产品目标与成功指标

3.1 产品目标

  1. 把"应该做什么"（分配现金流、按计划定投、按规则加码）变成系统里可勾选、可追踪的具体动作，而不是停留在用户脑子里的意图。
  2. 让用户在一个界面里看到"记账流水"和"投资持仓"共同构成的整体净资产，而不是两套互不相通的系统。
  3. 自动发现人工难以察觉的小额漏财，把"检查账单"从用户的待办事项里去掉。
  4. 数据默认离线可用、本地优先，云同步是增强而非前提，避免因为网络问题影响日常记账。

4.2 数据与设备模型

应用状态是单一的 WealthState JSON 对象，遵循「本地优先」原则：

  • 写入路径：任何变更先写入 localStorage（按 uid 隔离的 key），成功后异步同步到 Firebase Firestore；本地写入失败会通过事件提示用户"数据可能未持久化"，云同步失败则提示"云同步失败，本地副本安全"——本地永远是权威副本。
  • 版本迁移：状态带有 version 字段，加载时统一经过 migrateState() 做兼容处理（字段补全、历史脏数据修复、账户/交易的模糊匹配恢复等），保证跨版本升级不丢数据。
  • 版本历史（快照）：每次重大变更前会保存一份快照（最多保留 20 份），支持用户在 Settings 中查看历史并一键回滚。
  • 设备标识：每台设备生成一个 deviceId，用于区分多端写入来源。

5.功能需求

5.1 现金流与资金桶（Buckets）

  • 用户配置固定收支结构：津贴/工资、交通、餐饮、其他固定支出、不定期收入。
  • 系统据此计算「月度基础支出」与「月度可分配盈余」。
  • 用户可创建任意数量的资金桶（Bucket），每个桶有名称、金额、频率（月度 / 一次性）与备注，用于把盈余显性分配到具体用途（如安全垫、旅行基金、学习基金）。

5.2 安全垫（Emergency Fund）

  • 用户设定目标金额、当前金额、年化收益率（如放在货币市场基金）、月度追加金额。
  • 系统计算完成度百分比、预计达成目标所需月数，以及安全垫资金产生的预计年化收益。
  • 安全垫 100% 达成后，系统在顾问建议中提示可将资金重新分配到成长或自由桶。

5.3 定投计划（DCA Plan）

  • 设定月度定投总额与各标的（VOO / QQQM / 自定义 ticker）目标配置比例。
  • 系统基于实际交易记录计算加权平均成本、实际配置比例，并与目标比例比较得出"漂移"（drift）；单一标的漂移超过 8% 时，顾问建议会明确提示优先买入低配标的而非改变策略。
  • 支持最多 30 个自定义 ticker（大写字母数字符号，排除已有的 VOO/QQQM），用于跟踪 VOO/QQQM 之外的其他标的。

5.4 机会储备与熊市加码（Opportunity Reserve）

  • 用户设定机会储备总额与各标的分配。
  • 系统预设三档回撤触发梯度（如 -10% / -15% / -20%），每档对应固定比例与金额建议，并按 50/50 拆分 VOO/QQQM 的建议加码金额。
  • 每档状态显示为「未触发 / 已触发 / 已部署」，已部署的梯度不会被重复计入待部署清单。
  • 此储备在设计上与日常消费资金严格隔离，顾问建议会反复强调"不要挪用"。

5.5 投资持仓与交易记录（Portfolio）

  • 手动录入或 CSV 批量导入交易记录（日期、平台、标的、类型、金额、单位、手续费、汇率）。
  • CSV 导入支持两种格式：① moomoo 万能账户导出格式（自动识别 Symbol/Side 列，仅导入状态为 Filled 的订单，自动解析成交价与东部时区下单时间）；② 通用简化格式（按常见列名做模糊匹配）。
  • 持仓成本按买入顺序（FIFO 式加权）计算，卖出时按比例核销成本并结转已实现盈亏；卖空或无持仓下的卖出记录会被安全忽略而非产生负持仓。
  • 持仓列表显示：投入金额（MYR/USD）、持有单位、平均成本、实际/目标配置比例、漂移方向。
  • 交易时间线视图按标的展示历史买卖记录。

5.6 行情数据（Market）

  • 实时报价（价格、涨跌幅、开高低、成交量、市场状态）。
  • 基本面数据（股息率、市盈率、除息日、派息频率、费用率、总资产规模、历史回报）。
  • 历史价格与风险指标（最大回撤、夏普比率、Beta、波动率、当前回撤、胜率）。
  • 四类参考资产对比矩阵（广泛美股、成长集中、国际分散、单一持仓），不依赖实时行情请求，作为始终可用的参考基准。
  • K 线图表通过 TradingView 官方 Widget 嵌入。
  • 经济事件日历：当前为静态参考列表（如 CPI、FOMC 等周期性事件类型），明确标注"仅供参考、非实时数据"，不承诺具体日期的准确性。
  • 行情数据来自非官方 Yahoo Finance 接口，通过公共 CORS 代理转发（详见 §8 已知限制）。

5.7 记账本（Ledger）

  • 账户体系：银行 / 钱包 / 投资三类账户，每个账户有开户余额；支持从其他系统导入数据时按名称模糊匹配或自动创建"待确认"账户。
  • 分类体系：预置收入/支出分类，支持自定义。
  • 交易记录：收入、支出、转账三种类型；转账要求来源账户与目标账户不同（相同账户的转账会被判定为无效数据并丢弃）。
  • 按时间范围（今日/本周/本月/本年/自定义）、类型、分类、关键词组合筛选。
  • 账户余额、分类汇总、月度收支趋势、投资类资产占比（自动排除货币市场基金账户，避免虚增"投资占比"）均由记账数据实时推导。

5.8 漏财雷达（Money Leaks）

系统在记账数据上运行 8 类检测器，每类给出严重程度（高/中/低）、月度影响金额、年化影响、置信度、证据摘录与下一步建议：

检测器识别逻辑
订阅费審查激活中的经常性支出，标签命中常见订阅服务关键词（Spotify/Netflix/Adobe/Gym 等）
可避免的手续费备注或分类命中 fee/charge/penalty/interest/overdraft/ATM 等关键词的支出
重复扣款短时间内出现的相似金额/描述的重复交易
支出异常上涨某分类月度支出相对历史基线显著上升
异常单笔支出单笔金额显著偏离该分类的历史分布
预算超支某分类实际支出超出预算/历史均值的幅度
目标停滞目标（Goal）长期没有新增贡献或进度停滞
债务拖累负债的利息成本对现金流的持续侵蚀

5.9 目标（Goals）

  • 每个目标包含当前金额、目标金额、月度贡献额、备注，可选绑定到某个记账账户。
  • 绑定账户后，目标的"当前金额"会实时取该账户余额，而非手动维护的静态数字。
  • 总览页可指定一个"主要展示目标"；系统默认优先展示尚未达成的目标。

5.10 负债、经常性收支与净资产

  • 负债记录：名称、余额、年利率、最低还款额，用于计算总负债与净资产。
  • 经常性收支：标签、金额、类型（收入/支出）、每月出现日期、启用状态；系统据此预测"下一次发生日期"（对 2 月 31 日等不存在日期做安全回退，且不会跨月滚动到下个月）。
  • 净资产 = 记账账户余额之和（仅计正值）− 总负债，随交易/负债变化实时更新。

5.11 规则卡与顾问建议（Rules / Advisor）

  • 七张固定规则卡：月度现金流、DCA 强制令、安全垫、机会储备、熊市部署、年龄/阶段策略、数据安全。
  • 用户可对每张卡的标题/正文做个性化覆盖，也可以隐藏不需要的卡片。
  • 支持自由笔记（单条笔记与笔记列表两种形式，均有长度限制）。
  • 顾问建议模块根据当前状态（安全垫完成度、配置漂移、现金流盈余等）动态生成 5 条左右的建议文案，语气机械化、可执行，不做主观投资判断。

5.12 投资增长计算器

独立的复利增长情景计算器（React 孤岛组件，按需懒加载，不影响主应用的加载体积），用于探索"如果月供/回报率变化，N 年后资产会怎样"这类假设性问题，与主账本数据解耦。

5.13 月度复盘（Review）

  • 系统按月汇总记账收支、当月定投投入，计算"自律分数"：储蓄率贡献最高 40 分、DCA 达成率贡献最高 30 分、是否有记账行为贡献 30 分。
  • 用户可为每月复盘补充笔记。

5.14 设置、隐私与版本历史

  • 隐私开关：金额打码显示（适合截图/共享设备场景）、导出前二次确认。
  • 版本历史：查看/回滚最近的状态快照。
  • 默认模板：可将当前配置（不含具体交易）保存为默认模板，用于新设备或重置后快速恢复结构。
  • 数据导出：将完整状态导出为文件。

5.15 账户与云同步

  • 使用 Google 账号登录（Firebase Auth），持久化登录状态。
  • 登录后优先展示本地已有数据，云端数据异步拉取后再决定是否覆盖展示，网络失败时不影响本地数据的可用性。
  • 提供 Demo 模式（VITE_DEMO_MODE=true）：跳过登录、加载固定演示数据、禁止任何写操作，用于产品演示与设计评审，不接触真实用户数据。

5.16 安装与离线（PWA）

  • 支持"添加到主屏幕"安装（Android 走浏览器原生提示，iOS 走应用内引导说明）。
  • Service Worker 提供离线可用性。

7.非功能需求

7.1 隐私与数据边界

  • Firestore 安全规则按 request.auth.uid == userId 严格隔离，用户只能读写自己的数据。
  • 金额打码、导出二次确认作为可选的隐私保护层。
  • Firebase 客户端配置（apiKey 等）通过环境变量注入，本身不构成敏感凭据（受 Firestore 规则与授权域名保护）。

7.2 性能与可用性

  • 本地优先架构保证弱网/离线场景下核心记账功能可用。
  • 行情数据按数据类型分级缓存（报价类 30 秒、基本面/历史数据 1 小时），避免对上游接口的过度请求。
  • 投资增长计算器等非核心组件按需懒加载，不计入首屏加载体积。

7.3 数据可靠性

  • 本地写入失败（如存储配额超限）会显式提示用户"数据可能未持久化"，而不是静默失败。
  • 云同步失败会提示"云同步失败，本地副本安全"，不会因网络问题阻塞记账操作。
  • 关键状态变更前自动保存快照，支持手动回滚，降低误操作/数据损坏的影响。

8.已知限制与风险

行情数据链路脆弱 高 报价、基本面、历史价格均通过非官方 Yahoo Finance 接口获取，且依赖公共免费 CORS 代理（allorigins.win / corsproxy.io / codetabs.com）转发请求。这些代理没有可用性保证，是当前行情功能最大的单点故障来源。
经济日历为静态参考数据 中 Market 页面的"经济事件日历"目前是硬编码的周期性事件类型列表，不对应具体年份的真实日期，已在界面上明确标注"仅供参考、非实时数据"，但尚未接入真实数据源。
部署路径存在历史遗留 中 仓库中同时存在 Firebase Hosting 配置（firebase.json / deploy.bat）与 Vercel 部署配置（vercel.json / api/），需要确认哪一个是当前实际生效的部署目标，避免维护两套无人使用的配置。
单用户使用场景 低（设计如此） 当前架构默认一个 Firebase 项目服务一个人／一个家庭，没有团队协作、共享账本、权限分级等多用户能力；这是产品定位的既定选择，而非待修复的缺陷。
缺少自动化视觉回归 低 单元测试覆盖了核心业务逻辑（成本计算、记账筛选、状态迁移、漏财检测），但页面级 UI 变更目前依赖人工在浏览器中验证，尚无截图对比类的自动化回归。

9.路线图与待决策事项

9.1 短期（提升现有功能稳定性）

  1. 把行情数据请求迁移到自建的 Vercel Serverless 代理，替换掉公共 CORS 代理依赖。
  2. 确认并统一部署路径（Vercel 或 Firebase Hosting 二选一），下线未使用的配置。
  3. 为经济日历接入真实数据源，或明确将其降级为"下个季度再做"的功能。

9.2 中期（体验与工程质量）

  1. 把当前 ui.ts 单文件（约 3000 行）按页面拆分为独立模块，降低维护成本。
  2. 补充漏财处理率等产品分析埋点，让 §3.2 的成功指标真正可度量。
  3. 评估现有但未接入界面的文件上传（Blob）能力是否要正式启用，或从代码库中移除。

9.3 待决策事项

  • 是否要支持多资产类别（不仅限于美股 ETF），例如本地股票、加密货币、房产估值？
  • 漏财检测的阈值（如手续费关键词、异常支出判定）是否需要开放给用户自定义，还是保持系统默认以降低认知负担？
  • 是否需要在"自律分数"之上引入更细粒度的月度目标设定（而不是单一分数）？
