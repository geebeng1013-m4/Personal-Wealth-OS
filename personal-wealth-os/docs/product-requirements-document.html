1.产品概述

1.1 产品是什么

WealthUp（内部代号 Personal Wealth OS）是一个面向个人的理财操作系统。它不是一个只用来「看余额」的记账本，而是把一整套会强制执行的规则和一个诚实的月度反馈循环串成闭环：发薪后先把钱分格 → 按计划强制定投 → 日常记账 → 系统自动检测漏财 → 汇总为「财务健康」状态 → 顾问把状态翻译成可勾选的行动 → 月末复盘执行力。

核心假设：多数人理财失败不是因为不会算账，而是因为缺乏纪律系统和及时反馈。因此产品的每一条建议都必须可追溯——从一个观察到的事实（FACT），到赋予它意义的规则（RULE），到它带来的影响（IMPACT），最后落到一个具体动作（ACTION）。

1.2 要解决的问题

  • 现金流没有分配机制：发薪之后钱没有被提前「分格」，容易被日常消费吃掉，定投计划形同虚设。
  • 投资纪律依赖意志力：普通记账 App 不会提醒「这个月的 DCA 做了没有」，也不会在市场下跌时给出可执行的加码规则。
  • 小额漏财难以察觉：订阅费、银行手续费、重复扣款零散地藏在流水里，人工很难逐笔发现。
  • 投资持仓与记账是两套系统：券商导出的交易 CSV 和日常记账互不相通，用户看不到「记账余额 + 持仓市值」共同构成的真实净资产。
  • 马币成本被汇率猜测污染：美股订单本身只有美元金额，没有汇率。用「今天的汇率 / 导入当天汇率 / 交易日汇率」去折算，得到的都是用户从未真正付过的数字。
  • 行情页鼓励追涨杀跌：一个「即将公布的经济事件日历」本质上是在邀请用户对每日噪音做反应，而不是帮他在下跌中坚持买入。

1.3 产品定位与边界（Non-goals）

当前版本明确不做的事情：

  • 不是持牌财务顾问或投资建议服务——顾问模块给出的是基于规则的机械化提示，不构成投资建议，也不做市场预测或自动交易。
  • 不是多租户 SaaS——架构假设每个 Firebase 项目服务一个人 / 一个家庭，没有团队协作、共享账本、权限分级。
  • 不对接券商 API 做自动同步——交易数据通过手动录入或 CSV 导入（针对 moomoo 导出格式做了专门解析）。
  • 不做通用多币种记账系统——记账本身以 MYR 为准；MYR/USD 是唯一的多币种场景，且只在投资侧出现。
  • 不承诺行情数据的实时性与完整性——行情为「研究参考」，链路见 §8。

2.目标用户与使用场景

2.1 目标用户画像

主用户画像：年轻定投者

在校生或刚出社会的年轻专业人士，收入以固定津贴 / 月薪 + 不定期收入为主，正在用 moomoo 之类的券商定投美股 ETF（VOO / QQQM / VXUS 等），以 MYR 记账、以 USD 交易，风险偏好偏高、投资期限长（20–30 年）。痛点不是「没钱投资」，而是「没有把纪律坚持下去的系统」，以及「看不清一笔笔手续费和汇率到底吃掉了多少收益」。

2.2 核心使用场景

场景一：发薪日的资金分配

用户在 Budget（Buckets） 把到手津贴按既定比例分配到安全垫、成长（定投）、自由、学习、机会等资金桶，明确每个桶的月度 / 一次性金额，避免钱在到账当天就被日常消费吸收。

场景二：月度定投、换汇与交易导入

用户按 DCA Plan 配置的目标比例在 moomoo 下单，先把马币换成美元、再买入。用户在 Portfolio 通过 CSV 导入成交记录（自动识别 moomoo 万能账户格式，或退回通用列名匹配），并单独录入这几笔货币兑换记录（马币金额 + 美元金额）。系统据此计算持仓、加权平均成本、已实现 / 未实现盈亏，标注配置漂移是否超过 8% 阈值，并说明成本基础中有多少比例落在用户真正付过的汇率上。

场景三：市场下跌时的机会储备部署

大盘回撤时，用户在 Advisor / Rules 查看预设的三档「熊市加码」梯度（-10% / -15% / -20% 各对应一定比例的机会储备），并在 Market 页对照该标的真实的历史回撤记录——过去十年这样的下跌发生过几次、最深一次花了多久才回本——按规则而非情绪决定是否加码。

场景四：日常记账与漏财发现

用户在 Ledger 记录日常收支与转账，系统在后台跑 8 类「漏财」检测（订阅费、手续费、重复扣款、支出异常上涨、异常单笔支出、预算超支、目标停滞、债务拖累），在 Money Leaks 汇总为可操作清单，不需要用户逐笔翻账单。

场景五：看一眼「我现在的财务状况」

用户打开 Overview，「财务健康」把五个方面（安全垫、现金流、预算、计划执行、债务负担）各自判成 healthy / watch / action，取最差者作为总状态。健康卡只陈述事实（「安全垫已完成 60%」），把「补 200 马币」这类建议留给顾问。

场景六：月度复盘

月末，用户在 Review 查看系统给出的「自律分数」（储蓄率 + DCA 达成率 + 记账完整度加权），判断这个月的执行力，为下个月调整分配比例提供依据。

3.产品目标与成功指标

3.1 产品目标

  1. 把「应该做什么」（分配现金流、按计划定投、按规则加码）变成系统里可勾选、可追踪的具体动作，而不是停留在用户脑子里的意图。
  2. 让用户在一个界面里看到「记账余额 + 持仓市值」共同构成的真实净资产，且不会把一个券商账户的余额和它持有的股票重复计算。
  3. 让每一个马币金额都落在用户真正付过的汇率上；无法覆盖的部分如实标注为「未覆盖」，而不是假装成本基础全都有据可依。
  4. 自动发现人工难以察觉的小额漏财，把「检查账单」从待办事项里去掉。
  5. 数据默认离线可用、本地优先；云同步是增强而非前提。

4.2 数据与设备模型（本地优先）

应用状态是单一的 WealthState JSON 对象：

  • 写入路径：任何变更先写入 localStorage（按 uid 隔离的 key），成功后异步同步到 Firestore。本地写入失败会显式提示「数据可能未持久化」，云同步失败提示「云同步失败，本地副本安全」——本地永远是权威副本。
  • 登录时的合并策略：先立即渲染该 uid 的本地数据；云端数据异步拉取后，只有确实读到云端文档才覆盖展示；读取失败绝不当作「云端为空」，也绝不用本地覆盖云端。
  • 版本迁移：状态带 version 字段（当前 v19），加载时统一经 migrateState() 做兼容处理——字段补全、历史脏数据修复、账户 / 交易模糊匹配恢复、非法转账剔除、自定义 ticker 校验去重等，保证跨版本升级不丢数据，也不会因单个无效字段重置整个用户状态。
  • 版本历史（快照）：每次重大变更前保存一份快照（最多 20 份），支持在 Settings 中查看并一键回滚。
  • 设备标识：每台设备生成一个 deviceId，用于区分多端写入来源。

5.功能需求

5.1 现金流与资金桶（Buckets）

  • 用户配置固定收支结构：津贴 / 工资、交通、餐饮、其他固定支出、不定期收入。
  • 系统据此计算「月度基础支出」与「月度可分配盈余」。
  • 用户可创建任意数量的资金桶（Bucket），每桶有名称、金额、频率（月度 / 一次性）与备注，把盈余显性分配到具体用途。
  • 现金流数字是规划意图，仅在顾问明确评估某条规划规则时使用，绝不当作已记录的财务现实——记录现实一律来自 Ledger。

5.2 安全垫（Emergency Fund）

  • 用户设定目标金额、当前金额、年化收益率、月度追加金额。
  • 系统计算完成度百分比、预计达成所需月数、以及安全垫资金的预计年化收益。
  • 完成度 ≥ 100% 判为健康，≥ 50% 为 watch，否则为 action；100% 达成后顾问提示可将资金重新分配到成长或自由桶。

5.3 定投计划（DCA Plan）

  • 设定月度定投总额与各标的（VOO / QQQM / 自定义 ticker）目标配置比例。
  • 系统基于实际成交记录计算加权平均成本、实际配置比例，并与目标比例比较得出「漂移」（drift，带符号，负数表示低配）。
  • 单一标的漂移超过容忍度（allocation-drift-tolerance，默认 0.08）时，顾问明确提示优先买入低配标的，而非改变策略。
  • 支持最多 30 个自定义 ticker（大写字母数字符号，排除已有的 VOO / QQQM），格式校验与去重在迁移层完成。

5.4 机会储备与熊市加码（Opportunity Reserve）

  • 用户设定机会储备总额与各标的分配。
  • 系统预设三档回撤触发梯度（如 -10% / -15% / -20%），每档对应固定比例与金额建议，并按配置拆分各标的的建议加码金额。
  • 每档状态为「未触发 / 已触发 / 已部署」，已部署的梯度不再计入待部署清单。
  • 该储备在设计上与日常消费资金严格隔离，顾问建议反复强调「不要挪用」。
  • 回撤梯度与 Market 页的真实回撤频率联动（见 §5.8）：一份为「20% 下跌」预留的现金，取决于这种下跌是几年一次还是一代人一次，其规模应当不同。

5.5 投资持仓与交易记录（Portfolio）

  • 手动录入或 CSV 批量导入成交记录（日期、平台、标的、类型、金额、单位、手续费、汇率）。
  • CSV 导入支持两种格式：① moomoo 万能账户导出格式（自动识别 Symbol / Side 列，仅导入 Filled 订单，解析成交价与东部时区下单时间）；② 通用简化格式（按常见列名模糊匹配）。
  • 持仓成本按买入顺序加权计算，卖出时按比例核销成本并结转已实现盈亏；卖空或无持仓下的卖出记录被安全忽略，不产生负持仓。
  • 每个持仓给出：投入 MYR / USD、持有单位、平均成本、实际 / 目标配置比例、漂移方向、已实现盈亏、累计手续费、成本基础中属于手续费的部分。
  • 手续费单列为一项事实：券商按每笔订单收取最低佣金，小额下单时佣金比任何市场波动都更能拖累收益。系统同时给出「含费」与「不含费」的马币回报，让佣金以两者之差的形式可见。
  • 交易时间线视图按标的展示历史买卖记录。

5.6 货币兑换记录与真实汇率（Currency Exchanges） v3 新增

一笔美股订单不带汇率——券商的订单导出是纯美元，因为「把马币换成美元」是一个独立事件、有自己的记录。没有这些兑换记录，一个持仓的马币成本就无从谈起。

  • 用户录入每笔兑换：方向（myr-to-usd / usd-to-myr）、马币金额、美元金额、日期、备注。汇率由两个金额推导，不单独存储，因此永远不会和金额脱节，且天然包含实际付出的点差与手续费。
  • 兑换与买入的先后顺序不限（通常先换后买，但不绝对；记录只有日期没有时间），两种排列都支持、成本相同。
  • 采用加权平均资金池而非 FIFO 分批：现金余额里的美元是可替代的，一旦两笔兑换落进同一账户，就没有「后一笔订单花的是哪批美元」的事实。资金池还能自然处理再投入的卖出所得——卖出按美元既有的汇率返还，正确地不改变均值。
  • 拒绝虚构：无法被任何兑换记录解释的美元，如实报告为「未覆盖」，调用方保留该笔交易原有的数字。覆盖率对外暴露，UI 会说明成本基础有多少比例落在真实汇率上，而不是默默暗示全部如此。
  • 上限 MAX_CURRENCY_EXCHANGES = 2000，单条脏记录可被丢弃而不影响其余状态。
已知取舍 从 moomoo CSV 导入的交易本身没有真实的逐笔汇率，导入时会以「导入当刻」的实时汇率打标（券商订单导出没有 FX 列）。对这些交易，马币回报率与美元回报率之间的差额，部分是「用户何时按下导入」造成的假象，而非真实经历的汇率波动。两者并列展示时，以美元数字为准。

5.7 实时估值与净资产（Live Valuation / Net Worth） v3 新增

  • 拿到实时报价时，Portfolio 与 Overview 用市值而非成本来衡量配置比例——你现在承担的风险是股票今天值多少，而不是当初花了多少。全部持仓可定价时基于市值（allocationBasis = "market"），否则回退到成本口径（不混用两种口径）。
  • 估值字段区分「未知」与「零」：没有可用报价时保持 null，绝不从陈旧或零价格里编造；总额只覆盖能定价的持仓，不会因把未定价持仓当作一文不值而被悄悄缩水。valuationStatus 标注是 complete / partial / unavailable。
  • 净资产 = 记账账户正值余额之和 − 总负债；当某个投资账户被标记为 holdsTrackedPortfolio 时，净资产取组合的实时市值并忽略该账户自己的余额，避免把「手动维护的券商余额」和「它已经代表的持仓」加两遍。券商现金 / 货币市场余额是真正独立的钱，不得打此标记。
  • 实时价格只会重估净资产，不会改动投入资本、单位、成本或手续费；估值结果从不持久化、从不改动状态版本。

5.8 行情研究与持有历史（Market）

  • 实时报价（价格、涨跌幅、开高低、成交量、市场状态），按数据类型分级缓存（报价 30 秒，基本面 / 历史 1 小时）。
  • 基本面数据（股息率、市盈率、除息日、派息频率、费用率、总规模、历史回报）。
  • 组成与行业权重：ETF 的真实持仓与行业分布，随基本面接口更新。
  • 资产对比矩阵：由实时数据和用户自己的持仓符号驱动，用于横向比较（广泛美股、成长集中、国际分散、单一持仓等）。
  • 持有历史与回撤记录 v3 替换：取代原「经济事件日历」。基于一段价格序列纯函数推导——
    • 每一次相对前高至少下跌某阈值（默认 10%）的回撤：起点、最深幅度、到谷底天数、回本天数（仍在水下则为 null，如实表示尚未结束）。
    • 固定持有期结果：对历史上每一个可能的买入日，持有 1 / 3 / 5 年后是正是负，给出亏损占比、最差 / 中位 / 最好。
    • 触发历史：针对用户配置的加码阈值（-10 / -15 / -20%），这种深度的下跌历史上出现过几次、中位回本多少天。
    理由：Market 页自陈其目的是「理解持有与风险，而不是对每日噪音做反应」，一个「即将公布」的日历恰恰在邀请后者；真正帮助一个人在下跌中坚持买入的，是关于下跌本身的证据。
  • K 线图表通过 TradingView 官方 Widget 嵌入。
  • 行情数据来自非官方 Yahoo Finance 接口，经公共 CORS 代理转发（详见 §8）。

5.9 记账本（Ledger）

  • 账户体系：银行 / 钱包 / 投资三类，每个账户有开户余额、可选图标与颜色；导入外部数据时按名称模糊匹配或自动创建「待确认」账户。
  • 投资账户可选打 holdsTrackedPortfolio 标记，声明「这个账户持有的就是组合里那批股票」（见 §5.7）。
  • 分类体系：预置收入 / 支出分类，支持自定义。
  • 交易类型：收入、支出、转账；转账要求来源账户 ≠ 目标账户（相同账户的转账判为无效数据并丢弃）。
  • 按时间范围（今日 / 本周 / 本月 / 本年 / 自定义）、类型、分类、关键词组合筛选。
  • 账户余额、分类汇总、月度收支趋势均由记账数据实时推导；金额汇总四舍五入到分，避免二进制浮点在小数远端漂移出的噪音。

5.10 漏财雷达（Money Leaks）

系统在记账数据上运行 8 类确定性检测器，每类给出严重程度（高 / 中 / 低）、月度影响、年化影响、置信度、证据摘录。检测「发生了什么」与「该怎么办」是两件事：观察由 moneyLeaks.ts 产出，处置建议由 Advisor 按 FACT→RULE→IMPACT→ACTION 统一供给，两处措辞不会打架。

检测器识别逻辑
订阅费审查激活中的经常性支出，标签命中常见订阅关键词（Spotify / Netflix / Adobe / Gym 等）
可避免的手续费备注或分类命中 fee / charge / penalty / interest / overdraft / ATM 等关键词的支出
重复扣款短时间内相似金额 / 描述的重复交易
支出异常上涨某分类月度支出相对历史基线显著上升
异常单笔支出单笔金额显著偏离该分类历史分布
预算超支某分类实际支出超出预算 / 历史均值的幅度
目标停滞目标长期没有新增贡献或进度停滞
债务拖累负债利息成本对现金流的持续侵蚀

5.11 目标（Goals）

  • 每个目标包含当前金额、目标金额、月度贡献额、备注，可选绑定到某个记账账户。
  • 绑定账户后，目标「当前金额」实时取该账户余额，而非手动维护的静态数字。
  • 总览页可指定一个「主要展示目标」；系统默认优先展示尚未达成的目标。
  • 可为目标设定结构化的月度贡献规则（goal-contribution），供顾问评估贡献是否到位。

5.12 负债与经常性收支（Liabilities / Recurring）

  • 负债记录：名称、余额、年利率、最低还款额，用于计算总负债与净资产。
  • 经常性收支：标签、金额、类型（收入 / 支出）、每月出现日期、可选绑定账户、启用状态；系统据此预测「下一次发生日期」（对 2 月 31 日等不存在日期做安全回退，且不跨月滚动到下个月）。
  • 债务负担因子：无负债为健康，负债超过总资产为 action，否则为 watch。

5.13 财务健康读模型（Financial Health） v3 新增

唯一回答一个问题：用户当前的财务状况如何？只给事实与状态，不给建议、动作、跳转或 HTML，从不持久化。依赖方向严格单向：LedgerSnapshot → FinancialSnapshot → FinancialHealthSnapshot → UI。

因子判定阈值
安全垫（safetyBuffer）≥ 100% healthy，≥ 50% watch，否则 action
现金流（cashFlow）当月盈余 > 0 healthy，= 0 watch，< 0 action
预算（budget）未设限额或记录支出在限额内 healthy，超出 action
计划执行（planExecution）本月定投达标 healthy，否则 watch
债务负担（debtLoad）无负债 healthy，负债超过资产 action，否则 watch

总状态取五因子最差者（action > watch > healthy）。当 Advisor 存在紧急建议时，总状态也升到 action——但这个信号由调用方注入而非被本模块 import（否则分层会反转：Advisor 消费 health，不能反过来）。

5.14 顾问建议与行动中心（Advisor） v3 重构

  • 确定性、基于规则的建议，每条都可追溯为 FACT → RULE → IMPACT → ACTION：观察 → 赋予其意义的结构化 FinancialRule → 为何重要 → 一个具体下一步。无 AI、无市场预测、无自动交易。
  • 来源纪律：已记录事实（净资产、现金、记录月支出）来自 getFinancialSnapshot()；个人政策（安全垫下限、支出上限、DCA 金额、目标配置、漂移容忍度、储备梯度）来自 state.financialRules；组合成本基础与记账余额彼此隔离。
  • 建议 id 按「关注点」而非「结论」命名（如 advisor:emergency-fund），因此情况变化时同一张卡保持身份稳定。建议按需推导、从不持久化。
  • 行动中心：用户接受某条建议后生成一条 ActionRecord（pending / completed），只存执行状态和被接受时的动作文案，不复制建议本身——标题、严重度、影响、跳转全部留在 Advisor 侧按当前事实重新生成，避免陈旧。依赖方向：facts → recommendations → AdvisorSnapshot → ActionRecord，反向绝不成立。

5.15 规则卡与笔记（Rules）

  • 七张固定规则卡：月度现金流、DCA 强制令、安全垫、机会储备、熊市部署、年龄 / 阶段策略、数据安全。每张卡可个性化覆盖标题 / 正文，也可隐藏。
  • 结构化财务规则（financialRules）：安全垫下限、月支出上限、DCA 月额、目标配置、漂移容忍度、储备部署梯度、目标贡献——这些是个人政策 / 规划意图，绝不作为已记录余额来源。
  • 自由笔记：单条笔记与笔记列表两种形式，均有长度限制。

5.16 月度复盘（Review）

  • 系统按月汇总记账收支、当月定投投入，计算「自律分数」：储蓄率最高 40 分、DCA 达成率最高 30 分、是否有记账行为 30 分。
  • 用户可为每月复盘补充笔记。

5.17 计算器（TVM / 投资增长）

  • TVM 计算器：货币时间价值。给定现值、终值、每期付款、利率、期数五要素中的四个求第五个；无法求解或输入非法时如实报告，不返回假数字；结果对五要素与合计逐一给出，且不含 NaN / Infinity；纯函数、确定性。
  • 投资增长计算器：独立的复利增长情景计算器（React 孤岛组件，按需懒加载，不计入首屏体积），用于探索「月供 / 回报率变化，N 年后资产会怎样」这类假设，与主账本数据解耦。

5.18 设置、隐私与版本历史

  • 隐私开关：金额打码显示（适合截图 / 共享设备）、导出前二次确认。
  • 版本历史：查看 / 回滚最近的状态快照（最多 20 份）。
  • 默认模板：将当前配置（不含具体交易）保存为默认模板，用于新设备或重置后快速恢复结构。
  • 数据导出：将完整状态导出为文件（会带上当前 version）。

5.19 账户、云同步与 Demo 模式

  • Google 账号登录（Firebase Auth），支持弹窗与重定向两种流程，持久化登录状态。
  • 登录后优先展示本地数据，云端异步拉取后再决定是否覆盖展示；网络失败不影响本地数据可用性；订阅监听器在用户切换 / 退出 / 重新订阅时正确释放。
  • Demo 模式（VITE_DEMO_MODE=true）：跳过真实认证、用带专属 uid 的 mock 用户、加载固定演示数据、预览环境内的编辑仅存本地且与真实账户隔离，用于产品演示与设计评审。

5.20 安装与离线（PWA）

  • 支持「添加到主屏幕」：Android 走浏览器原生提示，iOS 走应用内图文引导。
  • Service Worker（public/sw.js）提供离线可用性；缓存版本随入口 / 静态资源变更提升，不长期保留不兼容的旧应用壳。
  • 离线时已保存的本地财务数据仍可访问；登录、同步、行情等依赖网络的功能明确显示不可用或缓存状态。

7.非功能需求

7.1 隐私与数据边界

  • Firestore 安全规则按 request.auth.uid == userId 严格隔离，用户只能读写自己的数据；修改数据访问模式时同步检查 firestore.rules。
  • 金额打码、导出二次确认作为可选隐私层。
  • Firebase 客户端配置通过环境变量注入，只含可公开的 Web 配置，访问控制依赖 Firestore 规则与授权域名。
  • 不在源码或缓存中保存密钥、服务账号、私有令牌或真实用户财务数据；日志不记录敏感财务数据或认证令牌。

7.2 性能与可用性

  • 本地优先架构保证弱网 / 离线下核心记账可用。
  • 行情数据按类型分级缓存（报价 30 秒、基本面 / 历史 1 小时），启动时 pruneMarketCache() 清理上一会话的陈旧缓存，避免 localStorage 无限增长。
  • 投资增长计算器等非核心组件按需懒加载，不计入首屏体积。
  • 并发请求防竞态：用户切换标的后，旧请求结果不得覆盖新选择的页面状态。

7.3 数据可靠性

  • 本地写入失败（如存储配额超限）显式提示「数据可能未持久化」，不静默失败。
  • 云同步失败提示「云同步失败，本地副本安全」，不阻塞记账操作；读取失败绝不覆盖云端数据。
  • 关键状态变更前自动保存快照，支持手动回滚；迁移保留旧数据，不因单个无效字段重置整个状态。
  • 所有金额、比例、数量、日期输入都校验，拒绝 NaN / Infinity / 负数等非法值；金融计算只用数值、不依赖格式化字符串。

7.5 测试与验证

  • 核心业务逻辑有 654 个单元测试（npm test 经 _test.mjs 运行），覆盖成本计算、实时估值整合、汇率覆盖、记账筛选、状态迁移、漏财检测、顾问快照与行动中心、TVM 求解、回撤 / 持有结果等；异步失败会被计入而非「先报通过再崩溃」。

8.已知限制与风险

行情数据链路脆弱 高 报价、基本面、历史价格均通过非官方 Yahoo Finance 接口获取，且依赖公共免费 CORS 代理转发。这些代理没有可用性保证，是当前行情功能最大的单点故障来源。行情失败时应用其余部分（记账、组合成本、健康、顾问）仍完全可用。
CSV 导入交易缺少真实逐笔汇率 中 moomoo 订单导出没有 FX 列，导入时以「导入当刻」的实时汇率打标。对这些交易，马币回报率与美元回报率之差部分是导入时点造成的假象。缓解方式：录入真实的货币兑换记录（§5.6），系统会用真实汇率覆盖成本基础，并暴露覆盖率；两者并列时以美元数字为准。
部署路径存在历史遗留 中 仓库中同时存在 Firebase Hosting 配置（firebase.json / deploy.bat / .firebaserc）与 Vercel 部署配置（vercel.json / api/），且同时有 package-lock.json 与 pnpm-lock.yaml。需确认当前实际生效的部署目标与包管理器，下线未使用的配置。
ui.ts 体量偏大 中 页面模板与事件绑定集中在单文件（约 6000+ 行）。维护成本较高，建议按页面拆分为独立模块。
单用户使用场景 低（设计如此） 架构默认一个 Firebase 项目服务一个人 / 一个家庭，没有团队协作、共享账本、权限分级。这是产品定位的既定选择，而非待修复缺陷。
缺少产品分析埋点 低 §3.2 中「漏财处理率」等指标目前只有计算逻辑，尚无独立的行为埋点。

9.路线图与待决策事项

9.1 短期（提升现有功能稳定性）

  1. 把行情数据请求迁移到自建的 Vercel Serverless 代理，替换公共 CORS 代理依赖。
  2. 确认并统一部署路径（Vercel 或 Firebase Hosting 二选一）与包管理器，下线未使用的配置与锁文件。
  3. 在导入 CSV 后引导用户补录当期的货币兑换记录，把成本基础汇率覆盖率尽快拉满。

9.2 中期（体验与工程质量）

  1. 把 ui.ts 按页面拆分为独立模块，降低维护成本。
  2. 补充漏财处理率、顾问行动完成率等产品分析埋点，让 §3.2 的成功指标真正可度量。
  3. 评估现有但未接入界面的文件上传（Blob）能力是否正式启用，或从代码库移除。
  4. 为页面级 UI 引入截图对比类自动化回归。

9.3 待决策事项

  • 是否支持多资产类别（不仅限美股 ETF），例如本地股票、加密货币、房产估值？
  • 漏财检测阈值（手续费关键词、异常支出判定）是否开放给用户自定义，还是保持系统默认以降低认知负担？
  • 「自律分数」之上是否引入更细粒度的月度目标设定（而非单一分数）？
